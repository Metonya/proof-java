# Evaluation and Selection of Open-Source Java Repositories for Test-Quality CLI Validation

Developing a static analysis and test-quality Command-Line Interface
(CLI) that correlates JaCoCo XML coverage reports with Java Abstract
Syntax Trees (ASTs) requires validating the tool against complex
open-source codebases. Reconciling compiled bytecode execution metadata
with source code ASTs introduces substantial structural challenges.
These include mapping inner class execution names, resolving dynamic and
parameterized test iterations, correlating abstract base class test
inheritance, filtering synthetic compiler-generated bytecodes, and
traversing multi-module project directory trees.

To ensure the CLI operates reliably, target validation repositories must
be selected according to strict build reliability, test suite volume,
structural diversity, and testing style representation.

## Technical Challenges in JaCoCo XML and JUnit Source AST Analysis

The structural disconnect between compiled bytecode execution statistics
in JaCoCo XML reports and raw Java source ASTs requires specialized
parser logic. Evaluating static analysis tools against real-world
repositories exposes critical technical friction points that the CLI
must reconcile.

### Inner and Nested Class Name Mapping

JaCoCo XML reports record coverage for nested structures using binary
class name identifiers joined by a dollar sign
(package.OuterClass\$NestedTestClass). Conversely, Java AST parsers
represent inner classes as child nodes within the parent compilation
unit (OuterClass.java). The CLI must accurately resolve these
dollar-sign notation class names to their corresponding nested AST class
declarations across deeply nested test suites.

### Parameterized and Dynamic Tests

Modern testing features such as JUnit 5 \@ParameterizedTest and
\@TestFactory generate multiple runtime execution events in JaCoCo XML
reports while occupying only a single method declaration in the source
AST. The analysis tool must aggregate execution metrics across all
parameterized iterations and map dynamic runtime streams back to their
static source method anchors.

### Superclass Test Inheritance

Frameworks with extensive class hierarchies frequently define core test
assertion methods within abstract base classes, while concrete
subclasses instantiate specific target types. JaCoCo attributes executed
bytecode lines to either the concrete child class or the abstract parent
class depending on compiler optimization and method overriding. A robust
CLI parser must traverse class inheritance hierarchies across distinct
source files to credit code coverage accurately.

### Synthetic Methods and Bytecode Enhancements

Libraries using Lombok or extensive mocking frameworks like Mockito
generate dynamic proxy classes, synthetic methods, and implicit lambda
structures. JaCoCo tracks these generated bytecode structures, but they
lack direct source line representations in the AST. The parser must
detect and isolate synthetic bytecodes to prevent false-positive branch
uncoverage reports.

### Multi-Module Source Resolution

Multi-module project builds split compiled classes, JaCoCo execution
reports, and source files across distinct subdirectories. The CLI tool
must dynamically resolve relative package names in JaCoCo XML documents
against module-specific source roots, such as module-name/src/test/java,
ensuring accurate cross-module path mapping.

## Evaluation of Candidate Repositories

Ten candidate open-source Java repositories were evaluated against five
core selection criteria:

1.  Green default build on JDK 17+ using plain mvn test or ./gradlew
    > test.

2.  Native JaCoCo integration or trivial plugin addition.

3.  Primary reliance on JUnit 5, allowing limited JUnit 4 for legacy
    > robustness testing.

4.  Total test suite volume between \~500 and \~10,000 tests.

5.  High stylistic diversity, encompassing heavy Mockito usage, custom
    > assertion helpers or AssertJ, parameterized testing, and
    > multi-module build architectures.

### Detailed Candidate Profiles

#### Apache Commons Lang (apache/commons-lang)

Apache Commons Lang utilizes an Apache Maven build architecture
(pom.xml)^1^. The test suite has fully migrated to JUnit 5
(junit-jupiter), supplemented by extension libraries such as JUnit
Pioneer^1^. The repository contains approximately 4,500 test cases
structured within a single-module directory layout. Code coverage is
managed natively through the jacoco-maven-plugin configured with
explicit minimum coverage ratios^1^. The build is highly stable and
passes consistently across Java LTS versions 8, 11, 17, and 21^2^.
Apache Commons Lang meets all selection criteria, providing extensive
parameterized tests and standard utility assertion validation.

#### Apache Commons Collections (apache/commons-collections)

Apache Commons Collections operates on an Apache Maven build system
(pom.xml)^3^. It relies primarily on JUnit 5 (junit-jupiter-engine and
junit-jupiter-params)^3^. Containing roughly 4,200 tests, the repository
is organized as a single-module project. JaCoCo code coverage tracking
is natively integrated into the Maven build lifecycle with enforced
coverage thresholds^3^. Historical test flakiness, such as issues in
EmptyPropertiesTest#testSave, has been resolved in recent releases^4^.
The codebase meets all criteria and provides rich test inheritance
structures derived from abstract base test classes.

#### jsoup (jhy/jsoup)

The jsoup library uses a streamlined Apache Maven single-module build.
The test suite is fully upgraded to JUnit 5, comprising approximately
850 tests. JaCoCo integration is natively present in the build profiles.
The test execution is fast, deterministic, and free of known flakiness.
The project satisfies all criteria, serving as an optimal
small-to-medium benchmark for parsing document analysis code and custom
assertion structures.

#### Gson (google/gson)

Google Gson relies on an Apache Maven multi-module architecture
separating core logic from extras. The project incorporates
approximately 1,300 tests running primarily on JUnit 5 alongside minimal
legacy JUnit 4 helpers. JaCoCo is not enabled by default in the standard
test phase but can be trivially added by declaring the
jacoco-maven-plugin in the root POM. The build is green and stable on
modern JDKs. Gson satisfies all criteria and provides reflection-heavy,
type-token test edge cases.

#### Google Guava (google/guava)

Google Guava uses a multi-module Apache Maven structure (guava,
guava-testlib, guava-tests)^5^. Its test infrastructure is built
predominantly on JUnit 4 and uses dynamic test suite generators provided
by guava-testlib^5^. The combined test execution exceeds 25,000
individual test cases. JaCoCo is not natively configured in the parent
POM^5^, and executing the full suite requires significant memory and CPU
resources. Guava is excluded because it violates the maximum test volume
threshold (\~10,000 tests) and relies primarily on custom JUnit 4 suite
generators rather than modern JUnit 5 paradigms.

#### AssertJ Core (assertj/assertj-core)

AssertJ Core uses an Apache Maven single-module build. The repository
contains approximately 9,500 test cases written exclusively in JUnit 5.
It extensively uses \@Nested test classes, parameterized test suites,
and custom extension models. JaCoCo is natively configured with strict,
enforced coverage verification rules. The build executes reliably on JDK
17+. AssertJ Core satisfies all selection criteria and represents the
upper volume bound of the target criteria while providing complex nested
test structures and fluid assertion DSLs.

#### JUnit 5 (junit-team/junit5)

The JUnit 5 repository is structured as a multi-module Gradle project
built using the Kotlin DSL (build.gradle.kts)^8^. The project includes
approximately 4,000 tests distributed across subprojects such as
junit-jupiter-api, junit-jupiter-engine, and junit-platform-engine.
JaCoCo coverage reporting is natively supported via Gradle\'s JaCoCo
plugin and toggled using the enableJaCoCo build property^8^. The build
represents a gold standard of CI stability and executes cleanly on JDK
17+. The repository satisfies all criteria, offering Gradle multi-module
layout, \@Nested classes, and dynamic test factories (@TestFactory).

#### Spring PetClinic (spring-projects/spring-petclinic)

Spring PetClinic is a single-module Spring Boot application using Apache
Maven (pom.xml)^9^. The suite contains approximately 120 tests using
spring-boot-starter-test and testcontainers-junit-jupiter^9^. JaCoCo is
natively configured via the jacoco-maven-plugin^9^. The build is stable
and target JDK 17+ compliant^9^. Spring PetClinic is excluded because
its total test count falls far below the 500-test minimum threshold.

#### Dropwizard (dropwizard/dropwizard)

Dropwizard is a multi-module Apache Maven ecosystem comprising over
twenty modules (dropwizard-core, dropwizard-jersey, dropwizard-jackson,
dropwizard-hibernate)^10^. It contains approximately 4,500 tests. Core
modules rely on JUnit 5, while dedicated integration submodules
(dropwizard-testing-junit4) maintain legacy JUnit 4 support^10^. JaCoCo
is natively integrated across parent and module POMs^10^. The build is
stable on JDK 17+. Dropwizard meets all criteria, offering a
multi-module Maven structure, extensive Mockito usage, and mixed JUnit
framework executions.

#### JavaParser (javaparser/javaparser)

JavaParser uses a multi-module Apache Maven build (javaparser-core,
javaparser-symbol-solver-core)^15^. It contains roughly 4,000 tests
using JUnit 5 alongside legacy Hamcrest matchers^15^. JaCoCo is natively
configured via the jacoco-maven-plugin^15^. The build is green and
stable on JDK 17+^15^. JavaParser satisfies all criteria, introducing
AST domain logic tests, fixture file parsing, and Lombok bytecode
interactions^17^.

## Recommended Repository Suite and Edge-Case Ordering

To ensure comprehensive validation of the CLI tool, candidate
repositories are selected and ordered based on their capacity to expose
AST parsing and JaCoCo correlation edge cases. The final set consists of
a **Primary Recommendation Set (3 Repositories)** and a **Backup
Recommendation Set (2 Repositories)**.

### Primary Recommendation Set

#### 1. Dropwizard (dropwizard/dropwizard) --- Primary Selection #1

Dropwizard is ranked highest for validating multi-module aggregation,
dynamic proxy handling, and framework coexistence.

-   **Criteria Fulfillment**: Multi-module Maven build architecture^10^,
    > heavy Mockito integration, mixed JUnit 4 and 5 usage across
    > modules^11^, native JaCoCo plugin configuration^10^, \~4,500
    > tests, and green build stability on JDK 17+.

-   **Parser Edge-Case Rationale**:

    -   *Multi-Module Path Resolution*: Dropwizard splits code across
        > dozens of submodules^10^. The CLI must map JaCoCo XML reports
        > generated in module-specific target/ directories back to their
        > corresponding source files across discrete directory trees.

    -   *Mockito Synthetic Bytecode Filtering*: Intensive mocking of
        > HTTP, Jersey, and Jackson sub-systems creates dynamic proxy
        > classes and synthetic lambdas. The CLI parser must identify
        > and filter synthetic bytecodes present in JaCoCo XML that lack
        > matching source AST declarations.

    -   *Dual Framework Coexistence*: Including dedicated legacy
        > submodules (dropwizard-testing-junit4) alongside modern JUnit
        > 5 suites^11^ forces the parser to process both org.junit.Test
        > and org.junit.jupiter.api.Test annotation trees within a
        > single repository run.

#### 2. JUnit 5 (junit-team/junit5) --- Primary Selection #2

The JUnit 5 repository provides the ideal environment for testing
advanced language constructs, nested AST scopes, and non-Maven build
systems.

-   **Criteria Fulfillment**: Multi-module Gradle build using Kotlin DSL
    > (build.gradle.kts)^8^, native JaCoCo execution flags^8^, native
    > JUnit 5 engine capabilities, \~4,000 tests, and deterministic CI
    > build health.

-   **Parser Edge-Case Rationale**:

    -   *Nested Class Scopes (\$)*: Jupiter engine tests heavily employ
        > \@Nested test classes. The CLI must parse inner class AST
        > structures and resolve them against JaCoCo\'s binary
        > OuterClass\$NestedClass XML class attributes.

    -   *Dynamic Test Factories (@TestFactory)*: Tests utilizing
        > DynamicTest stream runtime test definitions from a single
        > source method. The CLI must correlate JaCoCo execution
        > coverage inside dynamic lambda streams without relying on
        > standard static \@Test method annotations.

    -   *Gradle Directory Conventions*: Incorporating a Gradle-based
        > build ensures the CLI handles non-Maven target layouts
        > (build/reports/jacoco) and multi-project task outputs^8^.

#### 3. AssertJ Core (assertj/assertj-core) --- Primary Selection #3

AssertJ Core tests the CLI against high test volumes, fluid method
chaining, and complex custom assertion assertions.

-   **Criteria Fulfillment**: Single-module Maven build, native JaCoCo
    > integration, extensive custom assertion DSL usage, \~9,500 tests
    > (near the 10,000 upper bound), and green build execution on JDK
    > 17+.

-   **Parser Edge-Case Rationale**:

    -   *Fluent Assertion Statement Matching*: AssertJ tests consist of
        > multi-line fluid method chains
        > (assertThat(\...).isNotNull().extracting(\...).contains(\...)).
        > Line coverage data in JaCoCo XML must be mapped to single AST
        > statement nodes that span multiple physical source lines.

    -   *Assertion Error Handling Scopes*: Soft assertion tests validate
        > failure states, generating non-standard exception-handling
        > branch structures in JaCoCo XML that the CLI must reconcile
        > against source AST nodes.

    -   *High-Volume Stress Testing*: With nearly 10,000 tests, AssertJ
        > Core validates the memory footprint and processing performance
        > of the CLI tool under heavy load.

### Backup Recommendation Set

#### 4. JavaParser (javaparser/javaparser) --- Backup Selection #1

JavaParser serves as the primary backup for testing AST code
manipulation and Lombok synthetic method edge cases.

-   **Criteria Fulfillment**: Multi-module Maven architecture^16^,
    > native JaCoCo plugin setup^15^, JUnit 5 with legacy Hamcrest
    > matchers^15^, \~4,000 tests, and clean JDK 17+ execution^15^.

-   **Parser Edge-Case Rationale**:

    -   *Lombok Synthetic Code Handling*: Interacts with Lombok
        > generated structures (e.g., \@Data, \@Getter, \@Setter)^17^.
        > JaCoCo reports coverage on Lombok-generated bytecodes that do
        > not exist in the source AST, testing the CLI\'s synthetic code
        > detection algorithms.

    -   *Fixture String Isolation*: Tests load and parse external Java
        > source code strings as test fixtures, requiring the CLI parser
        > to distinguish target project source ASTs from test data
        > strings.

#### 5. Apache Commons Collections (apache/commons-collections) --- Backup Selection #2

Apache Commons Collections acts as a backup for evaluating class
hierarchy traversal and abstract test inheritance.

-   **Criteria Fulfillment**: Single-module Maven build^3^, native
    > JaCoCo configuration^3^, JUnit 5 (junit-jupiter)^3^, \~4,200
    > tests, and reliable build performance^4^.

-   **Parser Edge-Case Rationale**:

    -   *Abstract Superclass Test Inheritance*: Core test suites inherit
        > assertion logic from abstract base classes (e.g.,
        > AbstractCollectionTest). JaCoCo records execution coverage
        > against either the abstract superclass or concrete child class
        > depending on bytecode compilation. The CLI must traverse class
        > hierarchies to attribute coverage correctly.

## Actionable Implementation Strategy

Validating the test-quality CLI tool should follow a phased execution
workflow across the recommended repository suite:

1.  **Phase 1: Single-Module AST & Fluent DSL Processing**\
    > Execute initial validation against **AssertJ Core**. This phase
    > validates parsing performance at high test volumes (\~9,500
    > tests), verifies multi-line statement coverage correlation, and
    > resolves \@Nested inner class identifiers.

2.  **Phase 2: Dynamic Execution & Non-Maven Layouts**\
    > Run the CLI against **JUnit 5**. This phase tests \@TestFactory
    > dynamic stream mapping, validates Gradle target path resolution
    > (build/reports/jacoco)^8^, and verifies engine-level extension
    > parsing.

3.  **Phase 3: Multi-Module Aggregation & Synthetic Bytecode
    > Filtering**\
    > Deploy the tool against **Dropwizard**. This phase validates
    > multi-module Maven path aggregation across subdirectories^10^,
    > tests synthetic bytecode filtering on Mockito proxies, and
    > verifies concurrent handling of JUnit 4 and JUnit 5 annotation
    > structures^11^.

4.  **Phase 4: Synthetic Method and Inheritance Fallback**\
    > If edge-case defects emerge during initial testing, expand
    > validation to **JavaParser**^16^ (to refine Lombok synthetic
    > method detection)^17^ and **Apache Commons Collections**^3^ (to
    > refine abstract superclass test inheritance resolution).

Executing this phased roadmap ensures the CLI tool is rigorously
validated against diverse build systems, source AST structures, and
JaCoCo XML coverage patterns.
